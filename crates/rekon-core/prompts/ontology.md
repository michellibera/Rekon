Map the code of the files on stdin onto the ontology whose TYPES and RELATIONS are listed there.
Nodes: elements these files define or configure that matter for the architecture and the data flow (components, interfaces, processes, data entities, transformations, events, data stores), external elements they talk to (actors, external systems, dependencies), and failure modes and observations the code makes explicit. Not every function is a node: a Process is an operation that matters on its own (a use case, a pipeline step, a job, a handler); constructors, getters and small helpers stay out. Usually 3-12 nodes per file.
An element listed under KNOWN ELEMENTS or SYMBOLS DEFINED IN OTHER FILES is not a node here: use it only as an edge end, with exactly that type and name.
Edges: relations between nodes, directed source -> target as described for each relation.
Evidence: every node and every edge needs at least one entry with "file" exactly as after "--- file:", "start" and "end" line numbers (the numbers before "|"), "symbol" (an identifier that appears in those lines) and a short "reason". A node points at its definition. An edge points at the exact lines of the call, read, write, emit or handler (usually 1-3 lines), with the called or used identifier as "symbol".
Names are in English even when descriptions are not, since names become identifiers: for code elements the identifier from the code, with functions and methods qualified by their module or type as in OUTLINE (e.g. init::run, Store::update); for other elements a short noun phrase. Descriptions and reasons: one short sentence each.
Report only what the code shows, with "confidence" from 0 to 1. Skip tests.
